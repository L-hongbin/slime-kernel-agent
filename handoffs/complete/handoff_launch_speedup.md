# 训练启动慢 排查 handoff（已完成，2026-06-07）

## 一句话结论

训练 job 启动慢（曾经 ~24 分钟）的根本原因，是**这台机器当时中了挖矿病毒、把 CPU 占满了**。
病毒清理后，启动只要 **~4 分钟**。所以"启动慢"基本随病毒清除而解决了。

为防再次发生：加了一个**启动前的宿主健康检查脚本**；另外有一个内核设置 `numa_balancing` 需要保持关闭（原因见第 3 节和附录，已自动处理）。

## 1. 到底发生了什么

- 一开始排查启动慢，以为瓶颈在各个软件阶段（权重加载、备份、引擎初始化……），查了很多但都对不上。
- 真正的原因：**宿主机的 224 个 CPU 核被一个挖矿病毒占满了（CPU 100%）**。病毒跑在我们容器**外面**，所以在容器里用 `ps`/`top` 根本看不到它——但 `/proc/loadavg`、`/proc/stat` 是**整机**的，能看到负载异常高（~600）。
- 运维清理病毒后，机器恢复空闲（CPU 99% 空闲）。**重新测：启动从 ~24 分钟降到 ~4 分钟。**
- 之前测到的各种"瓶颈"，**几乎都是 CPU 被占满时饿出来的假象**——干净机器上同样的阶段只要几秒到二十几秒（见第 4 节）。

## 2. 干净机器上的启动耗时分解（实测，总 ~4 分 11 秒）

| 阶段 | 耗时 | 说明 |
| :--- | ---: | :--- |
| Ray 集群启动 + 资源分配 | ~54s | 含 Ray 重启 |
| Python 重型库 import + 数据集加载 | ~31s | megatron / sglang / flashinfer 等 |
| 推理引擎（SGLang，2 个）启动 | ~71s | 含分布式初始化、权重加载 6–7s、CUDA graph 录制 7–8s |
| 引擎让出显存 → 训练 actor 开始 | ~22s | colocate 模式两者共用 8 张卡 |
| 训练 actor 建模 + 进程组初始化 | ~29s | |
| 加载参考权重 + 备份到 CPU + 优化器 | ~37s | |
| 首次权重同步（训练 → 推理） | ~5s | |

- **没有单一的大瓶颈了**，最大的两块是 **Ray 启动（~54s）** 和 **引擎启动（~71s）**。
- 如果以后还想把这 ~4 分钟再压一压，应该从这两块（import / Ray 启动 / 引擎启动）入手，而**不是**权重加载或备份——它们现在都已经是秒级。

## 3. 需要保持的设置 & 新增的工具

**(1) 保持 `kernel.numa_balancing=0`**（已在 `scripts/ray/start_cluster.sh` 启动时自动关闭）
- **为什么**：当 CPU 被占满时，开着这个内核特性会让两个推理引擎**互相争抢内存页**，把权重加载拖慢 10–20 倍。实验验证过：同样把 CPU 压满，开着 = 权重加载 56–135 秒，关掉 = 6 秒。CPU 空闲时则没区别（开关都 ~6–7 秒）。
- 我们的 colocate 训练本身就会占 CPU，所以**长期保持关闭最安全**，而且对我们这种已经绑好核的负载没有任何副作用。
- 机制和实验数据见**附录**。

**(2) 启动前宿主健康检查 `scripts/ray/check_host_health.sh`**（已接入 `start_cluster.sh`）
- 启动前检查宿主 CPU 是否被异常占满（就是为了**下次别再在被病毒/被别人占满的机器上跑而不自知**）。
- **默认会在宿主 CPU 异常繁忙时直接中止启动**（避免在被污染/被占满的机器上白跑）；设 `SLIME_REQUIRE_HOST_HEALTH=0` 可降级为只警告不拦截。

## 4. 排查过程中被推翻的结论（别再信）

病毒期间测出来的所有"某某阶段是瓶颈"——`load_checkpoint` 慢到 320 秒、权重备份 2.7 分钟、首次同步 115 秒、"H2D 拷贝占 38%"——**都是 CPU 被病毒占满时饿出来的假象**。干净机器上它们分别只要 ~20 秒 / ~13 秒 / ~4.5 秒，根本不是瓶颈。

**教训：先确认宿主机本身是干净、空闲的，再去 profiling 软件**——否则一切测量都会被外部负载带偏（我们就被带偏了很久）。

## 附录：NUMA 问题细节（为什么要保持 `numa_balancing=0`）

> ⚠️ 这部分的排查是在机器**中病毒、CPU 被占满期间**做的，所以当时记的绝对数字（80–104 秒、18 亿次页迁移等）被病毒放大了。**机制结论后来用实验验证过、是对的**；具体秒数按"病毒期数字"打折看。

**名词**：这台机器是双路（2 socket），有两个 NUMA 节点 node0 / node1（各是一组 CPU + 本地内存）。GPU0-3 属 node0、GPU4-7 属 node1，存放 checkpoint 的 NVMe 也在 node0。

**症状（病毒期）**：同时起两个 SGLang 推理引擎（各占 4 卡），绑 GPU0-3（node0）的那个，权重加载每次都比另一个慢 3–4 倍，100% 复现。

**原因（机制）**：checkpoint 的页缓存在 node0。两个引擎分处两个 node、同时读这批共享页时，开着 `numa_balancing` 的内核会不停把页在两个 socket 之间来回搬（page migration）；node0 引擎的缺页因此卡在内核的"等页搬完"（`migration_entry_wait`）。**CPU 越忙，搬页越慢、卡得越久**——这就是为什么病毒把 CPU 占满时它慢到 4 倍。

**实验验证（病毒清理后，干净机器）**：
- 机器空闲时：numa 开 / 关都 ~6–7 秒，没区别。
- 人为把 CPU 压满（模拟病毒，~560 个 CPU 占用进程）后：**numa 开着 = 权重加载 56–135 秒（node0 那个甚至跑不完）；关掉 = ~6 秒**。开着时页迁移次数也是关掉的 ~235 倍。
- ⟹ 慢的真因 = `numa_balancing 开着` × `CPU 被占满` 两者叠加。训练本身就吃 CPU，所以**保持关闭**。
- （备注：想把"CPU 满载下 numa=1 的权重加载时间"在反序下也复测一遍以彻底排除缓存/顺序干扰，但满载下 bringup 太慢、25 分钟窗口内没跑到权重加载，只拿到了"开着迁移 235 倍"这个与顺序无关的旁证。结论不受影响。）

**怎么关 & 影响**：
- `echo 0 > /proc/sys/kernel/numa_balancing`，已固化进 `scripts/ray/start_cluster.sh`（每次起 Ray 自动关；`SLIME_DISABLE_NUMA_BALANCING=0` 可退出）。跨重启持久化需运维 `sysctl kernel.numa_balancing=0`。
- 它是**整机全局**开关（影响机器上所有进程，不只我们）。对我们"已绑好核"的训练负载没有副作用、还更稳；唯一要注意：若这台机器混跑别的**没绑核**的任务，要把"关 numa_balancing"当成训练机的专属策略。
- 不改变任何计算结果，随时 `echo 1` 可还原。

**一个澄清（顺带验证过的）**：训练侧把权重备份到 CPU（pinned 内存）那一步，和 numa_balancing **无关**——pinned 页被 GPU 长期锁住、内核根本搬不动它（用 `migratepages` 实测每页都迁移失败）。所以那步的耗时是 `cudaHostAlloc` 本身的开销（干净机器上 ~13 秒），不是页迁移造成的。

> 当时还做过很详尽的逐条排查（~17 个假设：硬件、I/O、NCCL、cgroup 等逐一证伪），但那些数据大多在病毒期采集、已不具参考价值，故不在此保留；关键结论即上文。
