# 多轮 reward 设计分析

FastCredit 与 Correctness diff credit 都尝试在原 TRLOO 回报之外，补偿对后续答案有帮助的前轮。两者用不同的源码信号挑选受奖对象，但都没有直接证明该轮修改有用。本文比较这两个信号的含义与验证需求；公式、实现和实验记录分别由[组件奖励](component_reward_training.md)与[正确性 diff credit](correctness_diff_credit.md)维护

## 两种信号分别回答什么

| 方法 | 参照答案 | 选择前轮的依据 | 额外预算 |
|---|---|---|---|
| FastCredit additive | 正确且 speedup ≥ 1 的答案中，按现有质量分选最佳轮 | 最佳答案保留的组件及其最早可识别来源 | 最佳答案质量预算乘系数，早期来源获得对应份额 |
| Correctness diff credit | 首个有效正确答案 | CUDA、binding、ModelNew 各段与参照足够接近，且有实际 token 变化 | 固定总额，由不同的合格前轮版本均分 |

FastCredit 的 lineage 回答“这部分实现来自哪一轮，后来如何保留或恢复”。即使来源完全准确，被保留的修改也可能没有收益、拖慢程序，或只与后续修改组合后才有益；有的修改只保证编译或正确性，不提升性能

因此，lineage 可以定位候选修改并帮助构造对照。判断贡献还需要比较保留和移除该修改的结果，而且结论依赖其余实现与任务条件。进一步证明它对最终程序有用，也不等于证明模型当时做这一步改善了后续搜索，后者需要独立续跑验证

Correctness diff 用源码距离判断前轮离正确实现有多近。它容易覆盖局部修补，但 token 差异不区分关键公式修复、无关改名和新增实现。一个未完成但有用的前轮，也可能因为后轮补充了大量代码而超过阈值。分段比较、去重与实际入选案例见[方法与边界](correctness_diff_credit.md#怎样从代码-diff-得到-credit)

## 局部筛选怎样影响整轮学习

两种方法都在 turn-level 累计回报上加入 bonus，再计算同题、同轮的 leave-one-out advantage。受奖轮的原有效 response token 共同接受这一信号，包括有用代码、后来被修掉的错误和冗长 thinking。源码筛选没有把新增信号精确落到贡献部分；其它回答加奖时，未加奖回答的相对 advantage 也可能下降

Correctness diff 还存在先错后修的偏向：首轮直接正确没有额外项，首轮接近正确、后轮修复通过时则可能补偿首轮。两者都保留原 TRLOO 回报，不能仅据额外项断言先错后修的总奖励更高。均分不同合格版本也没有区分实际进展，例如中间版本只修正一部分错误，仍可能与更早版本分得相同预算。具体反例和训练 mask 合同见[Correctness 的风险分析](correctness_diff_credit.md#当前方法的问题与验证边界)

## 怎样判断是否值得继续

FastCredit step100 的同预算结果尚未显示全面收益；扩大 context 后，必须在相同推理预算下比较模型，不能把截断减少直接归因于 credit。24K／32K／40K、32K／48K／64K 对照及 FastCredit 更长 context 的单模型结果，由 [KernelBench 评测](../qwen38/kernelbench_eval.md)统一维护

Correctness diff 的 step100 已完成训练，固定集评测仍需按[评测交接](correctness_diff_credit.md#step100-固定集评测)处理客户端 abort 与完整分母验收。训练批次上的正确率、分奖覆盖和末批指标不能代替固定题集对照

后续验证需要分别回答三个问题：

- 受奖对象是否合适：人工检查入选与拒绝样例，并通过代码干预区分保留、接近与实际贡献
- 额外信号是否带来不希望的行为：联合观察首次正确位置、各轮与最佳正确率、回答长度、截断和实际 advantage，而不只看分奖比例
- 来源或 diff 选择是否优于普通补偿：使用等额外预算的分配对照，并记录随机对照实际改变了多少受奖对象；小样本高度重合不能作为独立支持

实验次序与后续对照候选见[研究计划](plan.md)。实现检查、单次评测与重复训练分别支持不同层面的判断，不应互相替代
