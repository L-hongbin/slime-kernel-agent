# 优化实现追踪的失败路径

我们希望从多轮生成中找出：最佳答案保留了哪些具体优化实现，它们最早出现在哪一轮，并据此把 reward 分给较早的轮次。探索先从源码匹配开始，随后加入执行记录、实际访存和 runtime 图，最后尝试用通用规则识别优化结构

这些尝试分别产出了可用的分析工具，却没有形成可靠、通用、适合直接分奖的优化实现追踪器。主要问题是追踪对象逐渐偏离目标：源码片段、存储依赖和优化标签都能被自动记录，但它们与“某一份具体优化实现”之间还缺少可靠的对应

本文作为历史失败路径记录，说明每一步为什么尝试、得到什么、哪里走不通。这里的失败指当时未达到上述目标，并非训练效果已经被证伪。当前单阶段源码分奖与训练验证另见[组件奖励方案](component_reward_training.md)

## 原本要追踪的是什么

例如，第一轮分别执行计算 A 和 B；第二轮把它们融合成一个 kernel F；第三轮保留 F，改好其它部分后得到最佳答案。我们希望把 F 的来源找到第二轮

F 是这个任务、这个计算位置上的具体融合实现。另一轮也写了一个带“融合”标签的 kernel，不足以说明它保留了 F；F 改了变量名，也不应立即断开对应。融合前的 A、B 与融合后的 F 可以视为不同组件，无需证明两种组织方式属于同一个组件

本轮接受“最佳答案中保留下来的实现值得 reward”这个假设，不要求先测出每个组件独立贡献了多少加速。因此，下面评判各条路径的重点是能否可靠识别和回溯具体实现，单项因果收益没有测清不是独立的否决理由

## 源码匹配：找到了文本留存，没找到稳定的优化实现边界

最初从每轮回答中提取 CUDA、binding 和 ModelNew，解析成函数、kernel、宏及 Python 方法。通过函数名和签名对齐组件，再比较规范化语法和局部 token 修改，追踪某段代码何时加入、何时被撤销、何时再次出现。随后又从最佳答案向前查找完整组件版本和局部代码片段的来源

这条路线成本低，也能回答明确的源码问题。例如，Qwen group118 的最佳版本恢复了较早的 cuDNN launcher，同时保留中间轮修改过的 pooling、BN 等 kernel，可以据此区分局部回滚与整份程序回滚

但自动命中的对象经常与我们想奖励的实现不一致：

| 实际案例 | 自动匹配看到什么 | 人工看到的实现变化 |
|---|---|---|
| DeepSeek group31 | 错误字符串、变量重命名等片段持续存在 | descriptor 缓存已经引入，但 helper 签名变化使它没有沿同一来源链延续 |
| DeepSeek group304 | 局部复用主要命中错误文案 | timestep 递推从 host 移入 kernel，后续保留递推并增加输入投影预计算 |
| Qwen group99 | 某些通用 helper 保留 | 全融合路线实际被放弃，最佳版本回到分段计算 |

这里暴露了两个相反的问题。匹配太严格时，改名、签名修改和代码搬动会使同一策略断开；放宽到局部片段时，又会把检查代码、错误文案和样板代码当成有意义的部件。扩大 token 匹配范围不能自动解决这个区别

源码工具因此保留为差分和定位工具。源码留存不能直接等同于优化实现留存，更不能把整段历史代码相同作为跨轨迹匹配的必要条件。具体审计见[源码候选人工核对](../../local_artifacts/paper/trajectory_candidates/manual_audit/review.md)

## 状态聚合的旁路：粗标签容易合组，手工结构又无法推广

另一条尝试是把不同轨迹中的相近状态聚到一起，供后续 advantage 计算使用。起初比较此前是否正确、最佳分数区间、上一轮结果、错误类型，以及 kernel 数量和库调用家族等摘要；严格版本则要求源码或历史内容相同

粗规则能聚到很多样本，却没有说明这些程序内部是否处于相近状态。“都编译失败”可能对应完全不同的实现和待修错误；kernel 数量相同也不说明计算组织相同。严格源码规则则几乎没有非首轮共同状态，无法提供足够的组内比较。匹配率本身不是有效性的指标

之后尝试从 reference 手工定义计算环节，在 MLP 和 MiniGPTBlock 上对齐参数、投影、mask、激活等位置。解释性更强，也能定位具体错误，但依赖人工选择环节和映射参数角色，扩展到几十 K 任务就会变成逐题或逐题型适配

这两种状态摘要都没有成为通用训练分组规则。后来状态匹配与组件追踪分别实现通用 runtime 观测，交叉核对部分结果；这种实现间一致只能支持被检查的记录，不能替代自然任务上的聚合效果验证。相关背景见[状态聚合记录](state_aggregation.md)

## 调用级 runtime：确认了执行行为，仍缺少计算部件的对应

为减少源码表面差异的影响，我们开始观察实际执行：记录 FFI 调用、GPU kernel、tensor 的形状和存储，以及库 handle、descriptor、workspace 等状态。模型构造后重复执行 forward，对照开启与关闭观测时的输出和开销

这一步确实补充了源码无法单独确认的事实。RNN 样本能看到每个 timestep 重复 launch 被改为一次 cooperative kernel；库 API 记录能够区分 descriptor 是重复创建还是持续复用，也能看到设置 workspace 后又被其它 API 操作改变

问题在于，调用记录主要回答“执行了什么”，参数和地址主要回答“传入了什么”，两者还不足以确认“哪个计算结果被后面使用”。同一块存储可以被原地更新、复用或通过不同 view 访问；同一个库 handle 的配置也可能在调用之间变化

一个微型检查中，native kernel 已经改写 tensor 内容，PyTorch 的版本计数仍然不变。这直接否定了用该计数判断任意 native 写入的做法。另一些调用虽然执行了，但只写入最终被丢弃的 scratch，不能因为它们出现在调用列表里就计入最佳答案的有效组件

因此我们进一步尝试从实际访存恢复数据来源。这次转向有明确的技术原因，但也让工作重心开始偏向构建完整的数据依赖，而不是识别具体优化实现。早期探针的实物检查见[runtime 人工核对](../../local_artifacts/paper/best_answer_credit/final/manual_review.md)

## 精确访存与 runtime 图：补齐了很多采集问题，仍没有完成目标

这条路线用 NVBit 给自定义 kernel 的访存插桩，把访问地址绑定到 tensor 存储，再按读写区域、写入版本和 stream 顺序建立调用间的数据边。受支持的库操作根据成功调用的 API 参数计算读写范围；从返回值向前查找相关调用，再比较不同轮次的实现和配置

图的节点始终可以保持在 kernel 或库调用级。变得过细的是构图所需的证据：为了确认一条来源边，采集器开始处理大量访存、原地操作顺序、别名、生命周期和并发关系

### 实际修过哪些问题

| 遇到的问题 | 已尝试的处理 | 仍留下什么 |
|---|---|---|
| 逐次访存记录很快超限 | 在 GPU 汇总精确读写字节集合，再导出连续区域 | 日志缩小，访存插桩本身仍有开销；大地址空间仍可能装不下 |
| 原地读写无法判断读取的是哪版数据 | 对符合条件的调用补充线程内顺序记录，重新执行完整 forward | 原子更新、跨线程关系和不完整记录仍可能无法确认 |
| 库内部实现庞大 | 用父级 API 规则表达读写，用实际二进制及入口标记版本 | API 覆盖不全、参数和实现版本缺失仍会中断对应 |
| 碎片区域导致 CPU 提图超时 | 改进区间算法并压缩重复摘要 | 能返回图不等于图已完整，也不等于跨轮匹配通过 |

这些修复有实际工程价值。但工程进展没有转化成相应的目标验证：能够看见更多调用和依赖之后，我们仍然难以稳定回答“中间轮引入的具体优化实现，是否被最佳答案保留”

例如，同样读取 A、B 并写 C 的两个 kernel，可以使用完全不同的计算组织；只看读写关系无法区分。加入严格机器代码指纹可以区分版本，又容易在合法修订、编译配置变化或模块变化时断开对应。我们再次遇到了“太粗会混淆，太细会断开”的问题，只是从源码层转移到了执行层

### 自然退化候选没有形成可靠的正例证据

在一次训练 batch 中，我们选择 reward 先下降后恢复的轨迹，检查中间轮是否引入了后来保留的新组件。唯一表面正例是 trajectory180：它的实现确实留存，但实际加速比持续上升，reward 下降来自 profiler 错误解析 `__launch_bounds__`，漏记了主要 kernel 的覆盖率

这个评分问题修复后，该例只能证明实现留存，不能再算“暂时性能退化后保留新组件”的正例。其它多数候选缺少完整证据，因此也不能从没有确认正例推断这种现象不存在。批次的最终分类见文末口径表及[裁定文件](../../local_artifacts/component_reward_training/library_binary_iteration/adjudication.json)

### 重放异常进一步暴露了目标与成本的错位

有些缺图来自采集器的容量或解码限制，有些来自候选真实越界和库调用失败。另有输出按字节哈希比较不一致的样本：并行浮点归约可能造成数值差异，但当时尚未保存充分的数值误差证据来确认原因和可接受性

这些情况应该分别记录，不能统称为工具失败。对于当前只关注加速比的范围，明确 runtime 失败的候选可以直接排除，无需为它们恢复完整组件图；对于正确运行的候选，仍需确认计时和观测代表的是哪份实现

这条路径的失败点，是把“完整精确图”当成追踪优化实现的前置条件，持续扩展了取证范围，却没有先验证这些细节是否能提高实现留存识别的有效覆盖。它不证明 runtime 分析不可能，也没有比较出 NVBit、CUPTI 或 Nsight Systems 谁是最佳选择；替换工具仍需要面对同一个组件定义问题

## 优化规则快验：离目标近了一步，但标签和整体函数仍不够

随后把注意力转回实现结构，用所有题共用的 AST 规则识别 shuffle、shared 数组读写、向量访问和 unroll 请求，再关联已有 profiling。只保留正确且计时有效的轮次，比较加速比，不继续处理运行错误

这版能找到真实的优化变化。例如 Qwen group266 从每线程串行点积改为 block 协作归约，DeepSeek group98 增加向量加载并调整分块。但这些识别结果仍有两层局限

第一，优化标签太粗。同一个“向量化”标签可能属于完全不同位置、不同实现；平均池化必需的除法也会满足宽泛的“归约后处理”条件。Qwen group99 放弃全融合后仍使用另一份向量化实现，标签持续存在不能解释为旧融合组件留存

第二，具体来源匹配仍依赖规范化的整个 kernel 源码结构和全局上下文。它可以容忍部分改名，却没有普遍解决局部修订、调用配置、helper 变化及作用位置的对应。因此，“按题型写规则”的问题虽然避免了，“怎样识别同一份优化实现”的核心问题还没有解决

同时，Qwen group9 的 float4 和 TF32 在同一轮引入，主要计时改善出现在 GEMM。这个例子说明，用标签与整版加速比的相关性验证识别器会产生误导。它不否定按最佳答案留存分奖的假设，也不要求先拆出单项收益；它要求我们先确认分给的是哪份实现，而非一个泛化标签

该次快验保留为候选筛选结果，没有直接进入训练 reward。具体结果和人工反例见[快验汇总](../../local_artifacts/paper/optimization_speedup_pilot/20260910_checked/summary.json)与[人工核对](../../local_artifacts/paper/optimization_speedup_pilot/20260910_checked/manual_review.md)

后续又尝试了局部变量的计算来源表示：对有限表达式规范化，把新 kernel 的写回值与旧 kernel 的中间计算匹配。构造例支持有限改写和 F5 中间值对应 F3 输出，但在固定代码后的 rollout121 训练留样中，没有增加旧方法以外的自然候选。作用域重复名字、未支持的内建/helper、输入加载方式变化都会拒绝或打断对应。这一轮说明原型支持面不足，尚未建立泛化收益，不证明通用分析在理论上不可行；详见[本轮人工核对](../../local_artifacts/paper/optimization_speedup_pilot/region_iteration_20260910/manual_review.md)

## 这条失败路径留下的约束

首先应明确要回溯的对象，再选择观测手段。“记录到的内容”不能直接充当“要奖励的组件”：源码片段适合定位，调用记录适合确认执行，访存图适合解释数据来源，优化标签适合分类，它们都需要和具体实现关联

通用性应通过固定规则后的新任务验证，不能靠不断追加题型适配获得。源码标准化和结构匹配可以继续使用，但应同时检查漏对应与错对应，特别是代码搬动、局部修订、融合后继续优化、放弃旧实现等情况

验证时还应把三件事分开：采集覆盖率、实现留存识别质量、训练收益。前两项的工程进展不能提前写成第三项成立；同样，尚未训练也不能写成方法已经没有收益

该阶段快验只观察正确实现的加速比，全错轨迹没有可用的性能终点。后续单阶段方案已把失败轮纳入源码观察，并允许其中的实现成为后续正确答案的来源；已有解析和人工样本可复用，完整低层依赖图不再是训练前置条件
